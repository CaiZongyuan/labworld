# 让开发持续形成可合并结果 — 2026-10-15

依据用户指定的[开发时间线](../../backups/maintenance-2026-10-15/timeline-summary/timeline.html)及其事件、GitHub 和 CI 输入，调整当前流程与仓库自有 PM skill。目标是尽早把一个完整小结果合入 main，并在无法交付时及时改变计划。

## 时间线支持的判断

历史已有 36 个 PR 合入；问题集中在最后一轮旧 Source V1：12 张实施票没有形成合入交付，多个候选重复验证共享代码。13 次有完整窗口的 CI/attempt 单次约 32–39 分钟，累计约 7 小时 53 分钟。累计包含并行重叠，不能等同于总人时或浪费时间。

记录支持的阻塞包括：共享消费者并行变动、正常入口与真实 wire 值核对较晚、多个堆叠候选重复完整检查、定向绿色未保留原失败前置条件，以及把给已结束 agent 的排队消息误认为重新启动。旧 #102 最终 Windows 已通过，剩余浏览器初始 readiness 失败的根因仍未确认。

独立审查确实发现了启动参数丢失、资产约束失效及跨语言 hash 不一致等问题，应保留。改进重点是切片、反馈入口与退出决策，不能把未知失败直接归为 flaky，也不能把减少检查数量当作效率证据。

## 已落实的流程

规则唯一来源是 [development-flow.md 的 Merge first](../agents/development-flow.md#merge-first)，AGENTS.md 和 PM skill 指向它。测试、文档、体验与 tracker 规则已对齐。

| 旧模式                                    | 当前规则                                                                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 多张票同时写，最后一起集成                | 默认一个实现项；第二个仅用于解除当前阻塞，或首片已合入且消费者独立；上限两个，未发布代码也计入                           |
| 大 PR 完整后才进入交付                    | 目标 200–500 行非生成新增，含测试；超过 1,000 行先重切或说明不可拆耦合及完成边界                                         |
| 没有合并但持续扩张                        | 4 个工作小时无可审候选就重切；8 个工作小时无实际合并就停止新功能派工并作出具体重排决定                                   |
| 红基线和产品功能混在同一分支修            | 核对实际 main/CI，已知红基线先作为一个有界修复处理                                                                       |
| 每个修复串行重复简化、双审、全量本地和 CI | 局部简化一次；一名非作者覆盖两轴，按风险使用第二名；冻结同一候选后审查与 CI 可并行，修复只刷新受影响证据                 |
| 不断换 probe、agent 或分支继续调查        | 同一失败最多两个工作小时或三个有区分度的尝试；达到边界必须选择修复、有证据的限定延长或明确 blocker，整体交付时钟继续有效 |
| 每张票都重演整个 Epic 或新写整套教程      | 在最便宜的有效公开接缝证明行为，浏览器覆盖真实接合与渲染；随票更新使用指南，完整教程序列在 Epic 收尾组织                 |
| 有日志、有预留角色就算在执行              | 用实际启动操作恢复 agent，收到启动确认或进程/ledger 后才报告运行                                                         |

时限包含任务实际推进期间的 CI 和诊断等待；明确暂停与未知历史区间分别记录。这是触发决策的上限，不是承诺任何问题都能按时解决，也不降低独立审查和最终 head CI 的要求。

## CI 工程仍需单独交付

本轮修改的是 agent 的执行规则。当前 GitHub workflow 仍执行完整 Linux、浏览器分片和 Windows 检查；没有新增 `ci:full`、quarantine 或轻量 PR 分流，不能按文字假定这些功能已存在。

接下来的工程顺序应是：

1. 核对当前 main 的必需检查；若仍是已知红基线，先处理一个有明确失败入口和退出条件的最小修复。避免把 #103 的新功能与这个修复混为一张 PR。
2. 用独立小 PR 实现可验证的 CI 选择规则：纯文档/流程改动走相关检查，产品变更执行受影响套件，风险或影响无法界定时运行完整覆盖。稳定的合并汇总检查必须能识别漏跑；规则和 GitHub 分支保护需与真实 workflow 一起核对，不能只加标签。
3. 按已知失败补齐一次运行即可取得的安全诊断产物。隔离测试需要真实不稳定证据、责任人、修复期限和实际非阻塞运行路径。合成账户不能单独证明 trace 中所有 token、URL 或请求头可公开。

这些是后续工程项，尚未发布实施票或开始修复产品 CI。#103 仍是唯一新产品参考规格，其四个工作包不是必须同时推进的四个实现分支。后续拆票应先找到一个真实示例经正常入口可验证、可独立合并的最小结果，再扩展场景和完整双浏览器同步。
