# 具身实验室教学/方案原始素材

> 原始教学与构想材料，保留导出格式供查阅。Foundation V1 的实施范围以 [GitHub 规格 #1](https://github.com/CaiZongyuan/labworld/issues/1)为准；开发入口见[交接文档](../handoffs/digital-twin-foundation-v1.md)。

> 问题：我正在做agent平台和具身智能黑灯实验室的结合，形成干湿闭环，现在agent平台有了，需要把重点放在具身智能黑灯实验室。首先整个实验室应该做到数字孪生，所有设备，机器人，物料和实验室信息可以通过，类似 Previewing the Model Hardware Standard \\ Anthropic 等协议同步到物联网/孪生平台，需要有可视化，最好有物理仿真（类似英伟达的仿真平台），当然threejs最好。请你广泛检索给出方案
>
>



我广泛查了一轮之后，结论比较明确：**不要把“黑灯实验室数字孪生”理解成一个 3D 大屏，也不要试图用一个协议统一所有东西。** 更合理的是把它做成一个真正的 **Physical Lab OS / Lab Twin Runtime**：下面接设备、机械臂、AMR、传感器和物料，上面接你的 Agent 平台；中间维护实验室的实时状态、空间世界、资源约束和执行状态。



Anthropic 8 月刚发布的 **Model Hardware Standard（MHS）** 与你现在的方向几乎完全重合：设备驱动把异构硬件统一成可发现的状态和操作，Agent 通过 MCP / CLI / API 使用；Genentech 的 PoC 正是“液体工作站 \+ 机械臂 \+ 酶标仪 \+ Agent”闭环。但目前 MHS 仍处于 research preview，尚未正式开源，因此我建议**按照 MHS 思想设计自己的硬件抽象层，但不要把系统绑死在 MHS 上**。\(\[Anthropic\]\[1\]\)



## 我建议的最终架构



核心不是单一 Digital Twin，而是三个相互连接的 Twin：



**Operational Twin** 管“现在实验室是什么状态”；

**Spatial Twin** 管“现实世界在哪里、能不能动、会不会撞”；

**Scientific Twin** 管“这个样品是谁、经历过什么实验、为什么得到这个结果”。



三者用统一 `twin_id` 联系起来。



这个架构有一个很重要的边界：



> **Agent 负责科学决策和高级任务规划，Lab Runtime 负责确定性执行，设备控制器负责毫秒级控制，Safety Controller 拥有最终否决权。**
>
>



LLM 不应该直接控制电机、阀门或者机械臂关节。

# 1\. 设备协议层：不要发明一个“大一统协议”



我建议采用如下分层。

|**场景**|**推荐**|**在你的体系中的角色**|
|---|---|---|
|Agent ↔ Hardware|**MHS\-compatible interface**|Agent 看到的统一硬件能力|
|实验室设备|**SiLA 2**|液体工作站、酶标仪、泵、天平、培养相关设备|
|工业设备|**OPC UA \+ LADS**|培养箱、离心机、分析仪器、PLC、复杂工业设备|
|机械臂 / AMR|**ROS 2**|运动、传感器、TF、导航|
|机械臂规划|**MoveIt 2**|抓取、碰撞检测、轨迹规划|
|多 AMR / 建筑资源|**Open\-RMF**|AMR 调度、交通冲突、门、电梯、Workcell|
|简单 IoT|MQTT 5|温湿度、门磁、电源、环境传感器|
|无标准协议设备|Vendor SDK / Serial / TCP / COM|写 Adapter|
|Agent 工具层|MCP|将高层 capability 暴露给 Agent|



### SiLA 2



SiLA 2 本身就是为实验室自动化设计的，基于 HTTP/2、Protocol Buffers 和 gRPC；它不是按照“设备品牌”建模，而是通过 Feature / Command / Property 表达设备能力，而且已经包含设备发现、安全、错误处理等机制。\(\[SiLA 快速集成\]\[2\]\)



所以例如：



```Plain Text
ThermoFisher X
Hamilton Y
Tecan Z
```



到了你的平台里面应该逐渐变成：



```Plain Text
incubate()
read_plate()
transfer_liquid()
shake()
centrifuge()
capture_image()
measure_temperature()
```



而不是让 Agent 学习每家厂商 SDK。



PyLabRobot 也很值得参考。它已经对 liquid handler、plate reader、pump、scale、heater shaker、robot arm 等做了 hardware\-agnostic Python abstraction，而且支持 SiLA、Modbus、Opentrons、xArm 等后端。它非常适合作为第一批 Adapter 的参考甚至直接复用。\(\[GitHub\]\[3\]\)



### OPC UA LADS



这是我认为你尤其应该关注的标准。



LADS 是 OPC Foundation 针对 Laboratory \& Analytical Device 的正式 Companion Specification，已经定义了：



**Hardware View**



```Plain Text
Device
 ├ Component
 ├ Nameplate
 ├ Calibration
 ├ Condition
 └ Maintenance
```



以及 **Functional View**：



```Plain Text
Functional Unit
 ├ Function
 ├ Program
 ├ Sensor
 ├ Controller
 ├ Actuator
 └ Result
```



它本身就覆盖 monitoring、control、program/result management、asset management 和 maintenance。\(\[OPC Foundation\]\[4\]\)



更值得注意的是，OPC Foundation 在 2026 年已经开始把 430\+ Companion Specifications 转换成适合 **RAG / MCP / Agentic AI** 使用的形式，所以它和你的 Agent 架构未来其实是趋同的。\(\[OPC Foundation\]\[5\]\)

# 2\. MHS 应该怎么放进去



MHS 不应该替代 ROS、SiLA 或 OPC UA。



它更适合成为：



```Plain Text
Agent
                  │
                 MCP
                  │
            ┌──── MHS ────┐
            │             │
      capability      safety metadata
            │
 ┌──────────┼─────────────┐
 │          │             │
SiLA2     OPC UA         ROS2
 │          │             │
设备       仪器/PLC       Robot
```



也就是说：



**MHS = Agent\-facing hardware abstraction。**



Anthropic 当前公开的信息里，MHS driver 会提供设备发现、状态和 procedure，并包含模型仅从代码中无法知道的物理信息和安全限制；同一个设备最终可以通过 MCP、CLI 或代码调用。Genentech 案例甚至处理了三台计算机、ActiveX/COM、文件投递式控制和 GUI\-only 设备，把它们统一成一套 state / procedure abstraction。\(\[Anthropic\]\[1\]\)



这和你未来黑灯实验室面对的设备碎片化非常像。



所以现在你可以自己定义：



```Plain Text
Lab Hardware Capability Contract
```



以后 MHS 正式开放时做：



```Plain Text
Capability Contract <-> MHS Adapter
```



而不是等 MHS。

# 3\. 数字孪生真正应该怎么建



我不建议把数字孪生简单定义成：



```Plain Text
device_id
status
temperature
```



黑灯实验室至少需要下面这些实体：



|Twin 类型|例子|
|---|---|
|Spatial|Lab、Room、Zone、Workcell、Station|
|Equipment|培养箱、离心机、显微镜、PCR|
|Robot|机械臂、AMR、灵巧手|
|Tool|Gripper、Pipette、Camera|
|Labware|Flask、Dish、Tube、96\-well Plate|
|Material|Cell、Media、Reagent|
|Inventory|Tip box、Tube rack、Bottle|
|Container|Incubator slot、Fridge shelf、Rack|
|Process|Experiment、Run、Task|
|Safety|Safety Zone、Interlock|
|Human|Operator / Approver|



每个对象至少包含五组信息：



```Plain Text
identity
state
spatial
capability
provenance
```



例如一个培养瓶：



```Plain Text
Flask_0042

identity:
  type: T75_flask
  batch: ...

state:
  status: culturing
  confluence: 72%
  contamination: false

spatial:
  parent: incubator_01/slot_B3
  pose: ...

content:
  sample: ipsc_batch_07
  volume: ...

provenance:
  created_by: passage_17
  last_operation: media_change_032
```



这样 Agent 才真正“知道实验室里有什么”。

# 4\. Operational Twin：我推荐 Eclipse Ditto



如果不想自己从零造 IoT Twin Backend，我会首先评估 **Eclipse Ditto**。



它非常适合维护：



```Plain Text
reported state
desired state
current state
```



同时自带资源级权限控制、REST/WebSocket API，以及 MQTT、AMQP、HTTP、Kafka 等连接方式。\(\[Eclipse Foundation\]\[6\]\)



比如：



```Plain Text
incubator-01

reported:
  temperature: 37.02
  co2: 5.01
  door: closed

desired:
  temperature: 37
  co2: 5

health:
  state: healthy

reservation:
  run_id: exp-0192
```



这比“把 MQTT topic 当数据库”好很多。



### BaSyx / AAS 要不要用？



Eclipse BaSyx 也值得研究，因为它实现的是工业界标准化的 **Asset Administration Shell（AAS）** Digital Twin，能表达静态 Submodel、动态 Submodel、资产数据、服务和仿真模型。\(\[Eclipse Foundation\]\[7\]\)



但是对你第一版，我**不会直接把 BaSyx 当核心 Runtime**。



我更倾向：



```Plain Text
Ditto
    Operational runtime

OpenUSD
    Spatial/physics runtime

PostgreSQL
    Scientific/provenance runtime

AAS
    Enterprise interoperability / export
```



这样会轻很多。

# 5\. 3D：强烈建议 OpenUSD 做源，而不是 Three\.js

我建议：



```Plain Text
OpenUSD = Source of Truth
Three.js = Web View
Isaac Sim = Physics Runtime
```

```Plain Text
Three.js Scene = Digital Twin
```



OpenUSD 已经不是单纯的 3D 文件格式，而是场景组合、层级、变体、引用和仿真资产描述体系。NVIDIA 现在已经明确把 OpenUSD 作为 Omniverse / Physical AI 的底层共同数据层。\(\[NVIDIA Developer\]\[8\]\)

```Plain Text

├─ environment.usd
│   ├─ room
│   ├─ door
│   ├─ bench
```

```Plain Text
     │     │
```


Real：







# 11\. 干湿闭环应该这样跑



你现有 Agent 平台的 ProtocolIR 可以继续保留。



整个链条我建议变成：



```Plain Text

      ↓
Hypothesis
      ↓
Experiment Design
      ↓
ProtocolIR
      ↓
Lab Compiler
      ↓
Executable Lab Plan
      ↓
Resource Validation
      ↓
Spatial Validation
      ↓
Physics Dry-run
      ↓
Safety Preflight
      ↓
Wet Execution
      ↓
Sensors / Images / Device Results
      ↓
Operational Twin
      ↓
QC / Analysis
      ↓
Agent Reasoning
      ↓

```



这里真正新增的核心是：



# Experiment Compiler



它把：



```Plain Text
“对 iPSC 做一次换液”
```



变成：



```Plain Text
reserve ARM-01

    move flask-37 → incubator-01/B3
```

这实际上就是你的 **Scientific Compiler → Physical Compiler**。



Autoprotocol 很适合参考它的 IR 思想，因为其目标就是把自然语言实验过程转成“无需人工解释、可直接映射到自动化硬件”的机器可执行协议。\(\[AutoProtocol\]\[15\]\)

# 12\. 执行层不要让 Agent 一步一步 Tool Call



这是黑灯实验室能不能稳定运行的分水岭。



错误做法：



```Plain Text
LLM:
move robot
wait
open incubator
wait
pick flask
...
```



正确方式：



```Plain Text
Agent
 ↓
generate plan
 ↓
validate
 ↓
compile deterministic program
 ↓
Executor executes locally
 ↓
Agent observes checkpoints
```



MHS 本身也采用类似思想：当任务长时间运行或要求速度高于在线模型推理时，把多个 driver command 组成代码，让设备自主执行，而不是让模型实时思考每一个动作。\(\[Anthropic\]\[1\]\)



Agent 负责：



```Plain Text
What / Why
```



Executor 负责：



```Plain Text
Exactly How
```



Robot Controller 负责：



```Plain Text
Every millisecond
```

# 1\. SiLA 2 到底是什么？



最简单的理解：



> **SiLA 2 = 给实验室仪器定义的一套标准化、可发现、强类型的远程控制接口。**
>
>



你是全栈工程师，可以先把它类比成：



```Plain Text
OpenAPI
+
gRPC
+
Device Capability Schema
+
Discovery
+
Observability
+
Standard Error Model
```



但它专门针对：



```Plain Text
laboratory automation
```



设计。



SiLA 官方自己强调一个非常重要的设计：



> SiLA 2 **关注 functionality，而不是 device type**。
>
>



也就是说它不希望你思考：



```Plain Text
Hamilton STAR 怎么调用？
Tecan 怎么调用？
某品牌酶标仪怎么调用？
```



而更希望你思考：



```Plain Text
这个系统具有什么能力？
```



例如：



```Plain Text
Temperature Control
Liquid Transfer
Plate Reading
Shaking
Incubation
Imaging
```



SiLA 2 使用 HTTP/2 和 Protocol Buffers，底层采用 gRPC 的 wire format；标准本身还定义了 Feature、Command、Property、Discovery、安全、错误等语义。\(\[SiLA 快速集成\]\[1\]\)

# 2\. 为什么这对 Agent 特别重要？



假设你没有 SiLA。



实验室里有：



```Plain Text
Thermo incubator
Olympus microscope
Hamilton liquid handler
Eppendorf centrifuge
某国产 CO₂ 培养箱
```



可能变成：



```Plain Text
Agent
  │
  ├── REST → Device A
  ├── COM → Device B
  ├── Serial → Device C
  ├── Vendor DLL → Device D
  └── TCP socket → Device E
```



Agent 上层必须知道一堆厂商差异。



这是非常糟糕的。



理想状态应该是：



```Plain Text
Agent
                  │
          Hardware Capability
                  │
              SiLA Client
                  │
         ┌────────┼────────┐
         ▼        ▼        ▼
      Server A Server B Server C
         │        │        │
       SDK A    Serial    COM
         │        │        │
       设备A     设备B     设备C
```



所以：



> **SiLA 并不要求设备厂家原生支持 SiLA。**
>
>



你完全可以在设备旁边部署一个 Adapter：



```Plain Text
Legacy Device
     │
Vendor SDK / Serial / COM
     │
SiLA Adapter
     │
SiLA Server
```



然后整个 Agent 平台只认 SiLA。



这就是它对你最大的价值。

# 17\. Feature Definition Language：FDL



那么设备到底怎么告诉别人：




```Plain Text

 ├ Commands
 │   ├ Parameters
 │   ├ Responses
 │   └ Errors
 │

```



然后工具链可以进一步生成：



```Plain Text

protobuf
 ↓
gRPC stubs
 ↓
Client / Server code
```

这点跟：



```Plain Text

```



非常类似。

# 1\. 先不要管 LADS，什么是 OPC UA？



OPC UA 的全称是：



**OPC Unified Architecture**



它最早来自工业自动化领域。



你可以暂时把它理解成：



> **一个能够把真实机器表达成“网络中的结构化对象”的标准体系。**
>
>



例如一台离心机，在普通 IoT 系统里可能就是：



```JSON
{
  "speed": 1200,
  "temperature": 4,
  "running": true
}
```



但 OPC UA 不满足于这么简单。



它希望表达：



```Plain Text
Centrifuge_01
│
├── Manufacturer
├── SerialNumber
├── Health
│
├── Rotor
│   ├── Speed
│   ├── MaxSpeed
│   └── Health
│
├── Lid
│   ├── State
│   └── Lock()
│
├── TemperatureController
│   ├── CurrentTemperature
│   └── TargetTemperature
│
├── Programs
│
└── Alarms
```



而且这些不仅仅是 JSON 字段。



它们存在于一个正式的：



# AddressSpace



里面。



OPC UA 官方定义里，AddressSpace 本质上是一组通过 `References` 互相连接的 `Nodes`；对象可以包含 Variables、Methods，并与其他对象建立关系。\(\[OPC UA在线参考\]\[1\]\)



---



# 2\. 把 AddressSpace 理解成“设备知识图谱”



这是对你最有用的理解方式。



传统 API：



```Plain Text
GET /temperature

POST /door/open

GET /health
```



OPC UA：



```Plain Text
Centrifuge_01
                   /     |      \
                  /      |       \
             Rotor      Lid      Health
              │          │
            Speed      State
              │
          1200 rpm
```



所以它其实更像：



```Plain Text
Typed Graph
```



而不是：



```Plain Text
REST endpoints
```



节点之间还有明确语义关系：



```Plain Text
Centrifuge
    HasComponent
        ↓
      Rotor

Rotor
    HasComponent
        ↓
      Speed
```



这对 Agent 很有意思。



因为 Agent 获取的不再只是：



```Plain Text
speed = 1200
```



而是知道：



> `1200 rpm` 是 `Rotor` 的 `Speed`，Rotor 属于 `Centrifuge_01`。
>
>



---



# 3\. OPC UA 里面最重要的几个东西



你现在先掌握四个：



```Plain Text
Object
Variable
Method
Reference
```



再加一个：



```Plain Text
Event / Subscription
```



---



## Object



代表一个实体。



例如：



```Plain Text

Rotor
Door
TemperatureController
```



和面向对象里的：




非常像。

## Variable



状态和数据。



例如：



```Plain Text

```



---



## Method



可以调用的动作。



例如：



```Plain Text

Reset()
```



OPC UA 官方实际上就把 Method 定义成由 Object 拥有的 callable function；Client 可以浏览设备支持的 Method，然后调用它。\(\[OPC UA在线参考\]\[1\]\)



所以：



```Plain Text

 ├ Variables   → state
 └ Methods     → actions
```



到这里你应该已经感觉：



> **这非常适合 Agent。**
>
>

# 4\. Reference 是 OPC UA 比普通 API 强很多的地方



比如：



```Plain Text

```

这已经开始有：



**Digital Twin**



的味道了。

非常重要的基础设施。

# 6\. 那么 LADS 又是什么？



现在就非常容易理解了。



OPC UA 只是告诉你：



> 我给你 Object、Variable、Method、Reference、StateMachine、Alarm……
>
>



但是没有规定：



> **“实验室设备应该怎么建模？”**
>
>



于是出现了：



# OPC UA Companion Specification



Companion Specification 就是：



> 在 OPC UA 这个通用语言上，为某个行业制定统一的领域模型。
>
>



官方定义也是“基于 OPC UA 的 domain\-specific Information Model”，并同时提供机器可读的 UANodeSet。\(\[OPC UA在线参考\]\[4\]\)



比如：



```Plain Text
OPC UA
   │
   ├─ Robotics
   ├─ Machinery
   ├─ AutoID
   │
   └─ LADS
        ↑
 Laboratory &
 Analytical Devices
```



所以：



> **LADS = 给实验室和分析仪器设计的 OPC UA 标准信息模型。**
>
>



它由 OPC Foundation、Spectaris、VDMA 等共同制定，是 manufacturer\-independent 的开放标准。\(\[OPC UA在线参考\]\[5\]\)

# 7\. LADS 最重要的设计：两个世界



这是这一节最值得记住的知识点。



LADS 把设备分成两个 View：



```Plain Text
LADS Device
              /         \
             /           \
    Hardware View    Functional View
```



也就是：



### Hardware View



> **这个机器“是什么”。**
>
>



### Functional View



> **这个机器“能干什么、现在在干什么”。**
>
>



官方规范就是明确按照这两个主要 View 来组织设备模型的。\(\[OPC UA在线参考\]\[6\]\)


```Plain Text

```

```Plain Text

```

> **Agent 的设备“事实层 \+ 资产管理层 \+ readiness context”。**
>

# 第四节：MQTT 5 —— 让实验室“发生的事情”流动起来



现在我们已经有：



```Plain Text

→ 设备能力

OPC UA + LADS
→ 设备结构、运行状态、Program、Result

Eclipse Ditto
→ 实验室 Operational Twin
```



接下来缺的是：

>
>



这就是 MQTT 最擅长的事情。



先记住一句话：



> **MQTT 不是设备语义标准，不是数字孪生，也不是机器人控制协议。MQTT 是一个轻量级的 Publish/Subscribe 消息传输协议。**

## 1\. 从最简单的例子开始



假设实验室里有个温湿度传感器。


这叫 polling。



MQTT 的思想不是这样。



传感器自己：



```Plain Text
Sensor

37.0
 ↓
publish

37.1
 ↓
publish

36.9
 ↓
publish
```



其他系统想知道，就：



```Plain Text
subscribe
```



所以：



```Plain Text
MQTT Broker
                  │
          ┌───────┼────────┐
          │       │        │
          ▼       ▼        ▼
        Ditto   LabOS    Dashboard
          ▲
          │
     Temperature
       Sensor
```



传感器不需要知道：



```Plain Text
谁在监听我？
```



Ditto 也不需要知道：



```Plain Text
传感器 IP 是什么？
```



两边通过：



# Broker



解耦。

# 2\. MQTT 最核心的三个概念



掌握三个就已经理解了一半：



```Plain Text
Publisher
Broker
Subscriber
```



例如：



```Plain Text
Incubator
    │
    │ publish
    ▼
MQTT Broker
    │
    ├────→ Ditto
    ├────→ Dashboard
    ├────→ Alert Service
    └────→ Historical Storage
```



培养箱只是：



```Plain Text
publish
```



它根本不在乎后面有几个消费者。

# 3\. Topic：MQTT 世界的“地址”



假设：



```Plain Text

```



培养箱发布：



```Plain Text
37.02
```



那么：



```Plain Text
topic:

payload:
37.02
```



其他程序：



```Plain Text
subscribe(
  "lab/cell-lab/incubator-01/temperature"
)
```



就能收到。

# 4\. Topic 可以形成层级



这是 MQTT 非常舒服的地方。



比如我们可以定义：



```Plain Text
lab/
├── environment/
│
├── devices/
│   ├── incubator-01/
│   ├── microscope-01/
│   └── centrifuge-01/
│
├── robots/
│   ├── arm-01/
│   └── amr-01/
│
└── sensors/
```



例如：



```Plain Text
lab/devices/incubator-01/temperature

lab/devices/incubator-01/co2

lab/devices/incubator-01/door

lab/devices/incubator-01/alarm
```

# 5\. MQTT 支持 wildcard



比如：



```Plain Text
+
```



代表单层。



```Plain Text
#
```



代表多层。



因此：



```Plain Text
lab/devices/+/alarm
```



表示：



> 所有设备的 alarm。
>
>



而：



```Plain Text
lab/#
```



意味着：



> 整个实验室所有 MQTT 消息。
>
>



MQTT 5 标准本身定义了 Topic Filter、single\-level `+` 和 multi\-level `#` wildcard。\(\[OASIS\]\[2\]\)

# 6\. 这对实验室非常有意思



比如 Alert Service：



```Plain Text
subscribe:
lab/+/+/alarm
```



就可以监听：



```Plain Text
Incubator alarm
Centrifuge alarm
Environment alarm
Freezer alarm
```



甚至一个 Agent Monitor 可以订阅：



```Plain Text
lab/#
```



观察整个实验室。



不过后面我会讲：



**不建议真的把所有原始 MQTT 数据直接喂给 Agent。**

# 7\. MQTT 最大价值：解耦



没有消息总线：



```Plain Text
Sensor
 ├── HTTP → Ditto
 ├── HTTP → Database
 ├── HTTP → Alert
 └── HTTP → Dashboard
```



新增一个消费者，就改一次传感器逻辑。



MQTT：



```Plain Text
Broker
                ▲
                │
              Sensor
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
    Ditto     TSDB      Alert
                          │
                      Dashboard
```



Sensor 永远只做：



```Plain Text
publish
```



新增消费者完全不影响它。



这就是 Pub/Sub 的价值。

# 8\. 那 MQTT 为什么特别适合 IoT？



主要三个原因：



### 轻量



Protocol overhead 很小。



### 长连接



通常保持 TCP connection。



### 异步



设备发生变化就主动推。



因此很适合：



```Plain Text
温湿度
门磁
CO₂
冰箱温度
设备健康
设备上线/掉线
运行状态
报警
任务事件
```



这种东西。



OASIS 标准也明确把 MQTT 定位为低传输开销、适合受限环境和 M2M/IoT 的协议。\(\[OASIS\]\[2\]\)



---



# 9\. MQTT 最重要的概念之一：QoS



MQTT 支持三个 QoS：



```Plain Text
QoS 0
QoS 1
QoS 2
```



这代表：



> **这个消息送达要保证到什么程度？**
>
>



---



## QoS 0



```Plain Text
At most once
```



意思：



> 最多送一次。
>
>



可能丢。



例如：



```Plain Text
temperature = 37.01
```



丢了一次无所谓。



因为 1 秒以后还有：



```Plain Text
temperature = 37.02
```



所以高速环境 telemetry 可以考虑 QoS 0。



---



# 10\. QoS 1



```Plain Text
At least once
```



意思：



> 一定努力确保送到，但可能重复。
>
>



例如：



```Plain Text
device_alarm
```



宁可：



```Plain Text
收到两遍
```



也不能：



```Plain Text
一次没收到
```



MQTT QoS 1 使用 acknowledgement 机制保证至少一次送达，因此消费者必须考虑 duplicate。\(\[OASIS\]\[2\]\)



这是我认为你的实验室 MQTT：



> **最常用的 QoS。**
>
>



---



# 11\. QoS 2



```Plain Text
Exactly once
```



目标是：



> 消息准确交付一次。
>
>



但是协议交互更多、成本更高。MQTT 5 使用更完整的双阶段确认流程实现 QoS 2。\(\[OASIS\]\[3\]\)



所以不要看到：



```Plain Text
Exactly once
```



就什么都 QoS 2。



一般：



|数据|建议|
|---|---|
|高频温度 Telemetry|QoS 0 / 1|
|Device state|QoS 1|
|Alarm|QoS 1|
|Task completed|QoS 1|
|控制相关关键消息|根据系统设计，不应单靠 MQTT QoS 保证|



---



# 12\. 一个很重要的工程事实



即使：



```Plain Text
MQTT QoS 2
```



也不等于：



```Plain Text
实验动作 exactly once
```



这两个概念完全不同。



例如：



```Plain Text
command:
dispense 10 ml
```



消息只交付一次，不代表：



```Plain Text
液体真的 dispense 了一次。
```



因为：



```Plain Text
Pump
→ 收到 command
→ 执行
→ 电机故障
```



或者：



```Plain Text
收到
→ 执行成功
→ ack 返回失败
```



应用层依然必须具有：



```Plain Text
command_id
execution_id
idempotency
state verification
result
```



所以：



> **MQTT delivery semantics ≠ physical execution semantics。**
>
>



这对黑灯实验室极其重要。

# 13\. Retained Message：非常适合状态



这是 MQTT 一个非常实用的机制。



假设培养箱发布：



```Plain Text
topic:
lab/incubator-01/door

payload:
closed

retain = true
```



Broker 会保存：



```Plain Text
closed
```



后来 Dashboard 才启动。



一订阅：



```Plain Text
lab/incubator-01/door
```



Broker 立刻告诉它：



```Plain Text
closed
```



不用等下次门发生变化。



MQTT 规范要求 retained publication 可以存储在 Broker 上，在后续匹配订阅建立时发送给 subscriber。\(\[OASIS\]\[3\]\)

# 14\. State 和 Event 要区分



这是设计 MQTT Topic 时非常关键的一点。



例如：



### State



```Plain Text
lab/device/incubator-01/state/door
```



内容：



```Plain Text
closed
```



适合：



```Plain Text
retain = true
```



因为我们关心：



> 当前是什么状态。
>
>



---



### Event



```Plain Text
lab/device/incubator-01/event/door-opened
```



内容：



```JSON
{
  "timestamp": "...",
  "operator": "...",
  "eventId": "..."
}
```



通常：



```Plain Text
retain = false
```



因为这是：



> 某件事情曾经发生。
>
>



区别就是：



```Plain Text
State
=
What is true now?

Event
=
What happened?
```



这对你的 LabOS 非常重要。

# 17\. Last Will and Testament：设备掉线检测



这是 MQTT 很经典的能力。



一个设备连接 Broker 的时候可以说：



> 如果我异常断线，请帮我发布这条消息。
>
>



例如：



```Plain Text
Will Topic:
lab/device/incubator-01/connectivity

Will Payload:
offline
```



正常连接的时候：



```Plain Text
online
```



设备突然断电。



它来不及自己发：



```Plain Text
offline
```



Broker 会替它发布 Will Message。



于是：



```Plain Text
incubator_01:

connectivity = offline
```



这对于无人黑灯实验室非常重要。



因为：



> **Agent 不仅要知道设备报错，还必须知道设备彻底失联。**
>
>

# 第五节：ROS 2 —— 机器人世界的“分布式神经系统”

# 4\. Node 怎么交流？

|类型|模型|适合|
|---|---|---|
|**Topic**|Publish / Subscribe|连续数据|

# 5\. Topic：连续感觉

```Plain Text
/camera/depth

/lidar/scan

/robot/pose
```

```Plain Text

```

