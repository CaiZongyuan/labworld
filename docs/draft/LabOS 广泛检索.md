# LabOS 广泛检索

> 原始构想与研究材料。Foundation V1 的实施范围以 [GitHub 规格 #1](https://github.com/CaiZongyuan/labworld/issues/1)和已接受 ADR 为准；接手开发请先读[交接文档](../handoffs/digital-twin-foundation-v1.md)。本文的远景和技术建议不自动成为首版要求。

> **一个向 Agent 提供可发现、可理解、可组合的物理能力，同时对真实执行承担权限、资源一致性、过程约束和结果验证责任的 Physical World Runtime。**
>
>



它不应该要求 Agent 理解每一种设备协议，也不应该把整个实验室都强行改造成 ROS 系统。Digital Twin、3D 引擎、仿真器和消息总线都可以成为它的组成部分，但**没有哪一个应该天然成为系统中心**。



我推导出的最小核心是：**能力契约 \+ 世界状态与物料账本 \+ 持久化执行状态机 \+ 边缘设备执行器。**



在这个核心之外，按实际需要接入机器人规划、空间模型、物理仿真和科学模型。独立的安全控制系统则始终保留最终否决权。



下文以 **2026 年 9 月 28 日前可核实的公开资料**为基础。“已有实机案例”“商业平台”“开源框架”“研究预览”会分别看待；它们都不自动等于经过安全认证的无人值守系统。

# 一、先厘清 MHS：方向重要，但不能把公开宣传当成完整执行规范

---

## 1\.1 目前能确认什么



Anthropic 于 **2026 年 8 月 27 日**发布 Model Hardware Standard 的研究预览，起源于与 HHMI Janelia 的合作。公开介绍包含标准化驱动、网络发现、读写原语、自然语言设备描述，以及 MCP、CLI 和代码 API 三种调用方式。官方同时明确：这是面向早期伙伴的预览，仍在为后续开源积累安全评估与实践。



截至本次调研，我没有找到足以独立实现和验证完整兼容性的公开规范、完整参考实现与一致性测试套件；官网仍以申请访问为入口。因此：



**MHS 值得作为兼容方向和设计参考，但现在不宜成为你的不可替换依赖。** 这不意味着预览内部没有相关机制，而是公开证据不足以让第三方验证其全部语义。

## 1\.2 MHS 真正值得借鉴的，不只是“用自然语言控制设备”



我的理解是，MHS 在推动三种转变：

1. **从“设备有接口”转向“设备能解释自己”。**  Agent 不仅需要函数名，还需要知道设备适用范围、参数含义、操作条件、风险和局限。

2. **从“为每种上层应用单独集成”转向“硬件能力可被不同 Agent 环境消费”。**  MCP、CLI、Python API 应该是同一能力的不同入口，而不是三个不同控制系统。

3. **从“模型逐步操纵硬件”转向“模型发现、编写和调用可复用技能”。**  Agent 可以参与技能开发，但经过验证的技能不必在每一步都调用模型。



第三点尤其重要：**Agent\-native 不意味着 LLM 必须占据实时控制环。**

## 1\.3 两个实机伙伴案例，比抽象愿景更有参考价值



**QuEra：AI 开发控制程序，确定性程序执行恢复。**



QuEra 的激光控制试验明确区分了开发与运行：Agent 通过 MHS 设计、编写和验证控制器，实际恢复由可检查的确定性程序执行，位于微秒级伺服环之上。其测试台报告了 700 次扰动测试中 695 次恢复成功，并通过独立波长信息确认没有“锁在错误状态却报告成功”。这是伙伴报告的测试台结果，不是对任意设备的安全保证。



对你的启示是：

> **让 Agent 产生候选技能，让工程流程验证技能，让 Runtime 调用已批准的技能。不要把未经验证的探索过程直接等同于生产执行。**
>
>



**Tetsuwan：统一设备接口，并没有消灭编译器、运行协调器和人工介入。**



Tetsuwan 的 ResearchOS 案例仍保留实验描述语言、编译器和 Runs Coordinator；未知错误恢复需要人工授权，案例中的某些恢复还需要人把物料搬到工作站之外的设备。它证明了接口统一的价值，但不能据此推断已经实现完全无人值守的通用实验室。



对你的启示是：

> **可以减少设备专用胶水代码，但不能省掉执行语义、授权和现实中的物料操作。**
>
>

## 1\.4 MHS 类思想还需要补上哪些契约



以下是我认为你的 Runtime 必须明确的内容，**不是在断言 MHS 内部没有这些能力**：

|**自描述设备通常能回答的问题**|**Physical World Runtime 还必须回答的问题**|
|---|---|
|这个设备有哪些操作？|当前这份样品、这套耗材、这个环境下允许哪些操作？|
|参数格式是什么？|参数之间、操作之间是否存在组合约束？|
|操作返回了什么？|物理效果是否发生、发生了多少、证据是什么？|
|设备是否在线？|状态是否足够新，是否满足启动条件？|
|命令超时了？|没执行、执行了一半，还是执行完成但响应丢失？|
|有哪些安全限制？|谁在什么位置强制执行限制，模型能否绕过？|



因此，我会把 MHS 类接口放在“**描述与接入契约**”位置，再用一个实验室级执行内核承担跨设备责任。

# 二、技术版图：几个不同问题，被经常混称为“实验室操作系统”

---

先把市场和开源生态拆成四类：

- **描述与发现层**回答“有什么、能做什么”；

- **执行与资源层**回答“谁能在何时对什么做什么”；

- **空间与控制层**回答“如何在物理空间完成动作”；

- **科学闭环层**回答“下一次实验做什么，结果意味着什么”。



它们有交叉，但不应该混成一个无边界平台。

## 2\.1 一个值得补进候选清单的方向：W3C WoT 与 LabThings



W3C Web of Things 的 Thing Description 已经提供 machine\-readable 的设备描述框架，包含 **Properties、Actions、Events、数据模式、协议绑定和安全描述**。这说明“硬件自描述”不是从 MHS 才开始；MHS 的新价值更偏向把这些能力直接接入模型的工作方式。



尤其值得研究的是 **LabThings\-FastAPI**：它用 FastAPI 和 Pydantic 为实验硬件实现 WoT 接口，采用 MIT 许可，也是 OpenFlexure Microscope v3 软件的底层框架。它比部署完整 IoT 平台更接近你所需的轻量设备描述与接口生成层。



我的判断：**可以借用 WoT 的描述结构，甚至复用 LabThings 的实现，但不必因此引入完整语义网、复杂本体或新的平台服务。**



同时，WoT 式 Actions 也不能自动替代样品流转、资源锁、物理执行恢复和结果验证。

## 2\.2 真正值得拆解的科研系统和工业实践



|**系统 / 项目**|**已有内容与证据层级**|**对你的价值及边界**|
|---|---|---|
|**UniLabOS**<br>|2025 年底预印本提出 Action、Resource 及物理资源流转建模，采用 ROS 2/DDS，并报告多类实机实验配置。|很接近“实验室物理内核”问题；尤其值得学习资源状态与操作效果的一致性，而非直接接受其全部技术栈。|
|**MADSci / WEI 生态**|MADSci 提供设备节点、工作站编排、资源、位置、实验、事件与数据组件；当前仓库标注 beta，Auth Manager 仍列在路线图中。|实验室语义比一般 IoT 平台更贴切，可以选择性复用；不能默认权限与安全边界已经完整。|
|**PyLabRobot**|MIT 许可的硬件抽象库，支持多种实验设备，并将资源模型与硬件 backend 分离，提供无需真实设备的可视化开发能力。|很好的驱动和实验操作实现来源；不是完整的实验室并发、安全或恢复内核。|
|**Bluesky / ophyd**|面向实验采集、硬件抽象、可组合实验计划、数据流和暂停恢复。<br>|对扫描、测量与自适应采集特别有价值；不必重新发明成熟采集引擎。|
|**AlabOS / ChemOS 2\.0**<br>|AlabOS 有公开的自主实验室工作流实现；ChemOS 2\.0 提供实验与计算编排的论文、代码和示例。<br>|说明“实验执行系统”有可借鉴的积累，不需要因加入 Agent 就全部重写。两者也不等于统一硬件标准。|
|**ChemAgents**<br>|2025 年 JACS 工作，以分层多 Agent、协议库、模型库与自动化实验室完成多步实机实验，并展示新实验室环境中的任务。<br>|证明上层科研决策与真实实验结合的可行性；它主要回答科学 Agent 如何工作，不直接回答通用基础设施如何标准化。|
|**RobotecAI RAI**|开源 ROS 2 Agent 框架，包含基于机器人资料生成能力描述及仿真、感知等工具。|值得借鉴机器人“自我描述”和工具发现；你已有 Agent 平台，不必再引入第二套完整 Agent 框架。|
|**Emerald Cloud Lab / Automata LINQ**|前者把实验仪器、样品与数据通过统一软件提供为服务；后者将自动化工作站、物料运输和软件集成。|工业实践提醒我们：真正的 Lab\-as\-API 必须连同装载、运输、耗材和异常处置一起设计，而不仅是包装设备 API。|



有两个选型细节需要特别注意：

- **UniLabOS 的许可不是“整个仓库统一开源许可”。** 当前 NOTICE 将主框架列为 GPL\-3\.0，而 `unilabos/devices/` 列为 DP Technology Proprietary License。框架与驱动需要分别评估复用条件。

- **SiLA 2 标准与某个 SiLA Python 库的维护状态也不能混为一谈。** 常见的 `sila2` Python 实现当前已标注停止维护，并指向 UniteLabs 的替代实现。选型应落实到具体实现、版本与设备驱动，而不是只看协议名称。

# 三、几种代表性架构路线：为什么我不建议从“平台选型”开始

---

下面是基于上述系统推导的架构比较。

|**路线**|**优势**|**主要问题**|**适用情形**|
|---|---|---|---|
|**设备直接暴露 MCP Tools**|接入快，Agent 使用自然<br>|跨设备锁、物料状态、长任务恢复容易散落；工具返回成功不等于物理成功|只读、低风险演示；或工具背后已有完整执行系统|
|**工业信息模型优先：OPC UA/LADS**|适合既有工业设备、统一信息模型和运维|不天然覆盖实验材料语义与机器人操作；全面改造成本可能高|PLC、工业设备占主导的实验室|
|**ROS 2 优先：所有对象都节点化**|机器人、传感器、坐标、规划接入自然|容易把样品和科学实验状态硬塞进机器人通信模型|机器人研发平台、机器人团队主导的系统|
|**Digital Twin 平台优先**|多设备状态、访问控制、可视化整合方便|容易先解决“看到什么”，后补“如何安全改变世界”|大规模资产与多租户状态管理|
|**能力与执行内核优先**|Agent 接口稳定，底层协议可替换；实验室语义集中|必须认真设计契约、资源与失败语义|**最符合你的目标**|



推荐的不是“自研一切”，而是：**自己拥有最小的跨设备语义与执行边界，其他专业功能优先复用。**



SiLA 2、LADS、ROS 2 都可以成为它的后端，而不是竞争谁成为整个实验室唯一语言。

# 四、Agent 应该看到什么：一个“可行动、但承认不确定性”的实验室

---

## 4\.1 核心抽象



我建议采用以下领域模型：

|**抽象**|**应表达什么**|**不应混淆什么**|
|---|---|---|
|**Entity**|具有稳定身份的设备、机器人、样品、容器、工位、区域|身份不能绑定易变 IP、串口号或 USD 路径|
|**Resource**|可占用、可消耗或有容量限制的资源|不只是设备；还包括夹爪、槽位、工作空间、耗材、物料数量|
|**Capability**|一个有参数、效果、约束和验证方法的能力|不是只有函数名和自然语言说明|
|**State / Observation**|已报告状态、估计状态、目标状态及其证据|`desired_temperature` 不等于实际温度|
|**Event**|有时间、来源与因果关系的状态变化或执行事实|不是任意日志文本|
|**Relationship**|包含、连接、装载、抓持、相邻、坐标依附等关系|物料所属关系不等于几何父子关系|
|**Constraint**|启动条件、全过程不变量、资源约束、权限与风险限制|不是只放在 prompt 里的注意事项|
|**Plan / Execution / Result**|候选方案、真实执行实例、结果及验证证据|计划完成、设备完成、实验质量合格是三个概念|



其中最容易被低估的是 **Resource、Observation 和 Result**。它们决定系统能否从演示走向可靠运行。

## 4\.2 Capability 应该是一份“物理效果契约”



例如，机器人不应该只暴露：

```Plain Text
move_to(x, y, z)
close_gripper()
open_gripper()
```



Agent 面向的生产能力更适合是：

```Plain Text
transfer_labware(labware, source, destination)
```



但高层名称本身还不够。下面是我建议的契约摘要，**不是 MHS 官方格式，也不是可直接执行的代码**：

```YAML
capability: labware.transfer.v1

inputs:
  labware: LabwareRef
  source: LocationRef
  destination: LocationRef

resources:
  exclusive:
    - labware
    - source
    - destination
    - robot
    - transfer_workspace

preconditions:
  - source_contains_labware
  - destination_is_available
  - labware_and_gripper_are_compatible
  - calibration_is_valid

invariants:
  - safety_zone_remains_permitted
  - grip_is_confirmed_while_carrying

effects:
  - labware_location_changes
  - source_becomes_available
  - destination_becomes_occupied

verification:
  - gripper_feedback
  - destination_presence_observation

failure_semantics:
  physical_retry: requires_reconciliation
  timeout_outcome: potentially_unknown
  cancel: approved_safe_checkpoint
```



实际实现还应包含参数单位与范围、能力版本、预计耗时、支持的取消方式、可用仿真模型、设备适用范围等。



**统一的是契约结构，不是抹平设备差异。** 两台设备都提供 `measure`，并不代表测量原理、精度、校准状态和样品兼容性相同。

## 4\.3 状态必须包含“不知道”



每个重要状态至少需要：

```Plain Text
value
unit
observed_at
received_at
source
sequence_or_version
quality / uncertainty
validity_or_freshness
```



我建议将以下情况明确区分：**已观测、已估计、已过期、相互矛盾、未知。**



例如，“夹爪最后一次报告有物体”不能无限期等价于“样品现在仍被可靠抓持”。数据库提供的一致快照，也不等于所有设备在同一个物理时刻被同时测量。



Agent 查询应能得到：**天平支持本次测量，但当前不可执行：校准状态已过期；样品位置需要复核。允许的下一步是请求校准或执行位置确认。**



这种“**能力 \+ 当前可用性 \+ 阻塞原因 \+ 合法恢复路径**”，比几千个工具描述更有用。

## 4\.4 文件系统隐喻有价值，但不能照搬



可以提供类似：

```Plain Text
lab://entities/robot-01
lab://entities/balance-01/capabilities
lab://samples/sample-042/history
lab://executions/run-118/result
```



让 Agent 像浏览文件系统一样发现对象、读取状态和追溯结果。



但物理世界里的操作不能简单等价为 `cp`、`mv`、`rm`：**样品转移不是改路径；分液不是复制文件；消耗不是删除数据库记录。**



这些操作必须走带资源约束和验证机制的执行接口。

# 五、推荐架构：一个小内核，几个可替换的专业后端

---

## 5\.1 总体结构



```Plain Text
已有 AI / Scientific Agent 平台
              │
       MCP / CLI / Python SDK
              │
┌─────────────────────────────────────────────┐
│ Agent-facing Gateway                        │
│ 发现、描述、查询、准备计划、提交、状态与结果   │
├─────────────────────────────────────────────┤
│ Physical World Runtime                      │
│                                             │
│ ① Entity / Capability Registry              │
│ ② World State + Material / Resource Ledger  │
│ ③ Admission + Durable Execution             │
│ ④ Event / Result / Provenance               │
└─────────────────────────────────────────────┘
          │                     │
          │                     ├── 仿真与验证后端
          │                     └── 空间查询 / 运动规划
          │
    Edge Executors / Device Adapters
          │
  SiLA / OPC UA / ROS 2 / SDK / Serial / GUI
          │
     仪器、机器人、传感器、PLC
          │
   独立安全控制、互锁、保护停止与急停
```



这里的四个内核模块是**逻辑边界，不要求是四个微服务**。



对于你的 MVP，我更建议：**一个模块化单体服务 \+ 一个持久化数据库 \+ 按设备隔离的边缘执行进程。**



先不要部署“每个概念一个服务”的分布式系统。

## 5\.2 模块边界与写入权



- **Registry** 管理稳定身份、能力定义、设备元数据、适用条件与版本。设备发现只产生待登记对象，不能自动获得执行权。

- **World State / Ledger** 管理观测、当前状态投影、物料数量、位置与操作历史。Agent 可以查询或提出更正请求，不能随意把“实际状态”改成自己希望的值。

- **Execution** 管理授权、资源预约、条件检查、任务持久化、执行、取消、验证与恢复。它是正常生产操作的唯一命令入口。

- **Edge Executor** 负责协议翻译、本地命令记录、设备反馈、超时处理与本地执行约束。云端 Agent 断线不应导致设备失去基本控制。

- **Safety Controller** 不依赖 Agent，也不依赖中央数据库或云端在线。它不只是 Execution 的一个可选插件。



最重要的边界是：**不能让 MCP、网页按钮、ROS 节点和运维脚本各自拥有互不知情的设备写入通道。**



确需人工接管时，应显式切换控制模式、撤销自动执行权，并在交回控制前重新确认状态。

## 5\.3 Agent\-facing API 应该小而稳定



我会围绕以下操作设计门面：

```Plain Text
discover(query)
describe(entity_or_capability)
query_state(selector, freshness_requirement)

prepare(intent_or_plan, target_world)
submit(prepared_plan_id)

get_execution(execution_id)
cancel_execution(execution_id)

get_events(cursor, filter)
get_result(execution_id)
```



这不是说所有实验都应塞进一个无类型的 `submit`。被发现的具体能力仍有严格参数 Schema；这些接口承担的是统一的发现和执行生命周期。



MCP 的最新公开规范入口目前指向 **2026\-07\-28**，已将 Tasks 列为扩展；Tasks 支持长任务句柄、轮询、运行中补充输入和重连后获取结果。因此不能再简单认为 MCP 只能同步调用。



但我的建议仍是：**执行实例由 Runtime 自己持久化，MCP Task 只是其协议层映射。** 更换 Agent 客户端、SDK 或 MCP 版本，不应丢失实验执行历史。

## 5\.4 异构设备如何接入



|**底层对象**|**推荐接入方式**|**统一到 Runtime 时必须补什么**|
|---|---|---|
|实验仪器|有原生 SiLA 2 就使用；否则厂商 SDK 或已有驱动|能力语义、耗材与样品条件、命令结果验证|
|PLC / 工业设备|使用既有 OPC UA；支持 LADS 时保留其信息模型|实验任务、材料与设备操作之间的映射|
|机械臂|厂商控制器技能，或 ROS 2 \+ 规划组件|抓持、工作空间、物料交接、执行后验证|
|AMR|厂商任务 API 或 ROS 接口|搬运资源、交接点、任务身份与跨车协调|
|相机 / 传感器|独立采集进程或既有 ROS 驱动|时间戳、标定、数据质量、观测对象身份|
|串口 / TCP / 旧 SDK|隔离进程中的协议适配器|状态机、单写入者、超时和失联语义|
|GUI\-only|隔离的专用会话与受控自动化|对话框检测、版本固定、独立结果观测、人工接管|



SiLA 2 已有 Feature、Property、Command 和可观测命令等结构；LADS 则提供实验与分析设备的 OPC UA 信息模型。它们不应该被简化理解为“只有传输协议”，已有语义应尽量保留。



不过，**没必要把每个旧设备先改造成 SiLA Server，再包成 ROS Node，再映射为 Twin，最后再暴露 MCP。** 设备适配器直接实现统一能力契约，往往更简单。



对于 GUI\-only 设备，我建议增加明确的自动化等级：如果无法可靠区分“未执行”和“已执行但界面异常”，它就不应该被当成可无人值守的通用执行器。

# 六、Digital Twin：需要“孪生能力”，不一定需要“孪生平台”

---

## 6\.1 应拆成四种视图



|**视图**|**主要内容**|**我建议的初始实现**|
|---|---|---|
|**运行视图**|设备状态、可用性、资源占用、执行进度|当前状态投影 \+ 新鲜度信息|
|**历史视图**|命令、事件、观测、故障与审计|追加事件记录 \+ 数据文件|
|**空间视图**|坐标、几何、位置、装配、抓持关系|布局模型 \+ 变换查询|
|**科学视图**|样品组成、批次、处理过程、测量结果、不确定性|样品与实验账本 \+ 科学数据模型|



它们需要关联，但没有理由被强行塞进一个产品或一种数据结构。



尤其要避免：**Twin 里写了样品在 B 工位，就认定真实样品已经从 A 到了 B。**



更合理的过程是：

```Plain Text
确认在 A
→ 预约转移
→ 转移执行中
→ 位置暂不确定或处于搬运中
→ 获得 B 工位的到位证据
→ 确认在 B
```



Twin 是对现实的有证据状态估计，而不是现实本身。

## 6\.2 Eclipse Ditto 应放在哪里



Ditto 提供设备数字表示、状态访问、策略控制和通知等能力；其官方也明确，它不是覆盖所有环节的端到端 IoT 平台。



我的判断：

- **如果你需要大规模、多租户、跨系统的设备状态访问与策略管理，Ditto 有价值。**

- **如果你只有一个实验单元、几个设备，PostgreSQL 中的实体、状态投影、事件和权限模型通常足以支撑第一版。**



与其问“有没有比 Ditto 更新的 Twin Platform”，不如先问缺口是什么：

- 缺工业资产交换：研究 AAS / Eclipse BaSyx。

- 缺实验室资源与位置语义：研究 MADSci、UniLabOS。

- 缺空间物理预测：研究仿真与机器人规划。

- 只是缺一个当前状态 API：自己实现薄层可能最合适。



**这些不是同类产品的简单排名。**

## 6\.3 存储不要过早复杂化



我的 MVP 建议是：PostgreSQL 保存实体、关系、能力、执行、资源预约和关键事件；图片、波形、视频、原始实验文件进入文件或对象存储。



采用“状态投影 \+ 追加事件 \+ 事务性 outbox”即可起步，**不必一开始就实现完整事件溯源架构**。



高频视频和控制遥测也不应全部经过 Agent 工具接口。Agent 主要消费摘要、异常、选定观测和结果引用；原始数据按需检索。

# 七、3D / Spatial World Model：先统一身份和坐标，再选择文件格式

---

## 7\.1 至少有三种不同关系，不能混为一棵树



**语义包含关系**：样品在孔中，孔属于板，板属于批次。

**连接关系**：泵连接管路，管路连接容器；设备连接电源或气路。

**坐标关系**：相机相对工位、工位相对机器人基座、夹爪相对法兰。



另外还需要表达动态的**装载和抓持关系**。



UniLabOS 对逻辑资源组织与物理连接的区分值得参考；它提示我们，实验室并不只有机器人常见的几何变换树。

## 7\.2 OpenUSD 是否是最佳选择？



**作为复杂 3D 资产组合与交换格式，它是很强的候选；作为整个实验室的权威状态模型，不是。**



OpenUSD 的核心价值是场景描述、资产组合、图层和可扩展模式，而不是资源预约、执行恢复或样品账本。



对你的选择建议是：

- **固定工作站、少量设备：** 先用布局 JSON、机器人描述、简化碰撞几何和标定文件。

- **多仿真器、大量 CAD、复杂资产协作：** 再引入 OpenUSD。

- **已经确定以 Isaac Sim 为主要仿真环境：** 可以较早采用 USD，但不要把实验室运行状态只存进 USD。

## 7\.3 ROS TF、USD 和真实空间如何统一



ROS 的 tf2 用于维护与查询坐标变换；它适合机器人运行时的坐标关系，但不替代样品与实验领域模型。



我建议建立显式映射：

```Plain Text
Entity ID
  ↔ Runtime spatial frame
  ↔ ROS frame_id
  ↔ USD prim path
  ↔ Simulator object ID
  ↔ Device-specific position reference
```



每条关键空间信息还要带上坐标约定、单位、时间、标定版本和来源；不确定性由你的模型额外表达，不能假定坐标系统本身已经替你处理。



应指定**每类数据的权威来源**：例如机械结构来自批准的资产文件，标定来自校准记录，动态姿态来自运行时观测。不要让浏览器、TF、USD 和仿真器彼此无条件双向覆盖。



ROS 社区的 `openusd-schemas` 已在推进 ROS 与 USD 的共享模式和工具；这是值得跟踪的互操作方向，但采用前仍需检查目标工具对具体模式的支持。

## 7\.4 Three\.js 不必“只是画图”，但不宜成为安全边界



Three\.js 可以承担布局编辑、标注、回放、交互检查和浏览器中的空间预览；它本身有完整的场景、对象与几何处理能力。



但我不建议让浏览器场景直接成为生产权威状态：**拖动一个设备模型，应产生一个布局变更提案，而不是悄悄修改真实设备的校准坐标。**



编辑、校验、批准、标定、部署，是不同环节。

# 八、Simulation：按风险增加保真度，而不是先建完整虚拟实验室

---

## 8\.1 优先建设的仿真层次



|**层次**|**检查什么**|**推荐位置**|
|---|---|---|
|**契约与资源验证**|类型、单位、参数组合、样品身份、容量、资源冲突、顺序|所有执行前的基础检查|
|**离散事件 / 设备状态机仿真**|设备忙闲、耗时、耗材消耗、故障、失联、部分完成|最先实现的仿真后端|
|**运动学与碰撞验证**|可达性、抓取姿态、路径与空间冲突|有机器人运动变化时|
|**动力学、接触与感知仿真**|抓持、碰撞响应、视觉、复杂运动|有明确需求时|
|**科学过程模型**|实验机理、测量响应、材料变化|独立的校准模型或代理模型|



MoveIt 的 Planning Scene 已提供机器人状态、环境、碰撞和约束检查的基础；这类功能不必为了 Agent 重新实现。



但是，运动仿真通过，不代表移液精度、混合效果或科学实验结果一定正确。**机器人仿真和科学过程仿真必须分开评价。**

## 8\.2 Isaac Sim 与替代方案



- **Isaac Sim** 适合复杂传感器、视觉、合成数据以及 NVIDIA 生态下的机器人仿真。需要纠正一个旧印象：现在已有公开的 Isaac Sim 应用源码，仓库代码采用 Apache 2\.0；但 Kit SDK、模型和纹理等附加组件适用其他条款，不能把整个依赖栈视为同一开源许可。

- **MuJoCo** 是需要动力学与接触建模时值得优先评估的较轻方案。

- **Gazebo** 更适合已有 ROS 系统、移动机器人和传感器集成测试。

- **Newton** 是值得关注的新开源物理引擎方向，采用 Apache 2\.0、围绕 Warp 等技术构建；但它是物理引擎，不是现成实验室执行平台，也不因为开源就消除了 GPU 技术栈依赖。



对你的 MVP，我的默认选择是：**设备状态机仿真先行；机器人需要时增加运动学验证；只有明确遇到接触或视觉问题，再引入物理引擎。**

## 8\.3 Sim 与 Real 应共享什么



共享：**能力 Schema、任务生命周期、资源语义、错误分类、事件格式和结果结构。**



不共享：**凭证、实际资源空间、设备地址、控制权限和模拟器专用管理操作。**



我建议使用不可混淆的执行目标：

```Plain Text
sim://cell-a/snapshot-123
real://cell-a
```



而不是在生产代码中随处传一个可变的 `dry_run=true/false`。



仿真器中的 teleport、spawn、delete 等管理操作不能映射成真实硬件能力。ROS 的 `simulation_interfaces` 正在统一仿真环境管理接口，这很有用，但与实验技能接口是两层不同抽象。



仿真报告也不应只有绿色的 PASS，而应包含：

```Plain Text
PASS / FAIL / UNKNOWN / NOT_MODELED
验证覆盖范围
使用的模型与标定版本
未建模效应
```



**仿真是准入证据之一，不是通用安全证明。**

# 九、安全行动：把“能做”与“获准做、做到了”彻底分开

---

这里最重要的不是再加一个审查 Agent，而是明确控制责任。机器人单元的设计与集成还应结合具体风险评估；ISO 10218\-1/\-2 已有 2025 版本，其中第二部分面向工业机器人应用与单元集成。下面的架构建议不能替代具体设备的工程安全评估。

## 9\.1 决策权如何分配



|**角色**|**可以负责**|**不应获得的默认权力**|
|---|---|---|
|**Agent**|提出实验计划、选择已批准能力、在预算内选参数、分析结果、建议恢复|修改安全阈值、清除急停、跳过验证、随意写设备寄存器|
|**Runtime**|授权、资源预约、条件检查、任务推进、证据记录、恢复分流|假装自己具有底层实时控制能力|
|**Planner / Skill Executor**|生成或执行受约束轨迹、已验证操作流程、局部恢复|绕过权限和工作空间约束|
|**Device Controller / Safety System**|伺服、互锁、看门狗、安全停机与保护|依赖 LLM 在线才能维持安全|



Agent 可以在限定实验空间内做有价值的自主选择。限制不应只表现为“每个参数各有上下限”，还应覆盖参数组合、操作顺序、累计消耗和历史状态。

## 9\.2 一次动作的准入与执行流程



我建议采用：

```Plain Text
PROPOSED
→ VALIDATED
→ RESERVED
→ EXECUTING
→ VERIFYING
→ SUCCEEDED
```



另设明确分支：

```Plain Text
REJECTED
FAILED
PARTIALLY_COMPLETED
OUTCOME_UNKNOWN
RECONCILIATION_REQUIRED
```



执行链应完成以下责任：

- **准入时**解析稳定对象 ID、单位和能力版本，检查权限、材料适用性与资源预算。

- **预约时**原子记录资源占用和执行身份，避免两个任务同时支配同一台设备、同一份样品或同一片工作空间。

- **发令前**重新检查关键实时条件，避免“刚批准时安全，执行时条件已经改变”。

- **执行中**由本地执行器和控制系统维护全过程约束；不能指望 Agent 轮询及时发现所有变化。

- **执行后**根据约定的证据判断物理结果，再提交相应状态变化。



`prepare` 产生的批准记录应绑定计划内容、能力版本、相关标定和有效期；Agent 改了参数，就不能继续使用旧批准。

## 9\.3 锁、租约与重试：最容易把软件正确性误当成物理正确性的地方



首先，数据库事务只应用来短暂地提交预约和状态，不应在设备运行几分钟时一直持有事务锁。PostgreSQL 提供行锁和 advisory lock，但 advisory lock 需要应用主动遵守；它不会自动约束外部设备。



我建议在执行层增加：**持久化 operation ID、边缘命令日志、资源租约、控制世代号，以及设备入口处的 fencing 检查。**



其中 fencing 的意思是：旧执行器即使网络恢复，也不能继续用过期身份发出新命令。



但还有一个更关键的规则：

> **租约到期，不等于物理操作已经停止。**
>
>



不能仅因为控制进程掉线，就把机器人或正在反应的设备立即分给另一个任务。必须确认它已处于允许重新分配的状态。



对于非幂等动作，超时后的默认策略应是：

> **先确认现实，再决定是否重试。**
>
>



例如，分液命令超时可能意味着没有分液，也可能意味着已经分液但响应丢失。再次发送相同命令，不能被视为无害的软件重试。



使用 Temporal 等工作流引擎时也必须注意这一点：持久化工作流能改善软件任务恢复，但 Activity 的重试与幂等性仍需要应用自己设计。

## 9\.4 物理世界通常没有真正的 rollback



样品混合后，回滚数据库不会让它恢复原样。加热、消耗、污染、破坏性测量也一样。



因此应区分：

- **数据事务回滚**：撤销尚未发生的逻辑修改。

- **物理补偿**：执行经过批准的冷却、转移、清洗、隔离等操作。

- **停止并协调**：无法可靠恢复时，保留现场状态并要求确认。



同样：**收到取消请求 ≠ 已经取消成功。**



很多设备只能在安全检查点停止。停止也不一定意味着切断全部电源：某些场景下，安全状态可能需要继续通风、冷却或保持抓持。

## 9\.5 验证与审计应成为执行输出，而不是事后日志



每次执行最好返回两个独立结论：

```Plain Text
physical_execution_status
scientific_quality_status
```



例如：

> 物理操作完成，但测量质量不合格。
>
>



或者：

> 设备返回完成，但缺少足够到位证据，物理结果未知。
>
>



审计记录至少关联计划、操作者、能力与驱动版本、标定、批准记录、命令回执、观测证据和结果文件。失败、拒绝和人工接管也必须记录。



另外，自描述内容本身也要有信任边界。MCP 当前规范明确提醒，不应无条件信任工具描述和 annotations。设备说明书、错误字符串、图像中的文字，都不能成为越权指令。:chatgpt\-content\-reference\{index="34"\}



因此：**发现新设备，不等于信任它；识别新能力，不等于授权它；生成新驱动，不等于可以上线它。**

# 十、技术栈建议：哪些保留，哪些默认不装

---

## 10\.1 我会选择的 MVP 基础栈



|**层次**|**初始选择**|**原因**|
|---|---|---|
|能力模型|Python 类型模型 \+ JSON Schema；Pydantic 严格校验<br>|易于同时生成 API、文档和 Agent 参数结构；Pydantic 支持 JSON Schema 输出和严格模式。|
|设备描述与 API|FastAPI；需要 WoT 时评估 LabThings\-FastAPI|复用轻量接口框架，而非部署完整 IoT 平台。|
|Agent 入口|MCP \+ 同源 CLI / Python SDK|三种入口使用同一授权和执行实现|
|持久化|PostgreSQL \+ 文件存储|保存关键状态、任务、资源与事件；大文件独立存储|
|执行内核|有界、持久化的状态机；第一版工作站串行|缩小并发和恢复问题；不是仅用内存队列串联异步函数|
|设备驱动|厂商支持接口优先；合适时复用 PyLabRobot|避免重新实现设备协议。|
|机器人|已批准的厂商技能；需要动态规划时才上 ROS 2 / MoveIt|固定工位不必先构建通用机器人平台|
|仿真|同接口 fake backend \+ 故障注入|首先验证运行时语义|
|运维界面|简单设备、任务、异常与空间视图|先能解释失败，再追求漂亮 3D|



如果你选择复用 MADSci 或 UniLabOS，应让它们承担明确的一部分责任，**不要在它们外面再复制一套资源与执行系统，形成双重权威**。

## 10\.2 对候选组件的明确判断



- **SiLA 2 / OPC UA / LADS：保留已有的，不强制全实验室统一到底层。**  它们解决设备互操作问题，统一 Agent 层负责跨协议一致体验。

- **ROS 2：机器人侧按需保留，不默认扩散到所有实验对象。**

- **MoveIt：需要运动规划和碰撞检查时使用；固定批准轨迹不必为了“架构完整”引入。**

- **MQTT：设备本来使用就接入，不把 topic 命名约定当作完整领域模型。** Sparkplug 能给 MQTT 增加工业数据与状态语义，但仍是互操作的一部分，不等于实验执行系统。

- **Eclipse Ditto：MVP 默认不装。** 当设备状态管理、多租户策略或跨平台集成成为真实问题时再评估。

- **OpenUSD：默认可后置。** 需要复杂资产交换或仿真生态时引入。

- **Isaac Sim / Omniverse：不是基础依赖。** 视觉、合成数据与高保真仿真需求明确后再选择。

- **Open\-RMF：单机械臂场景删除。** 它更适合多机器人车队与共享设施协调，不应成为一个固定实验单元的前置条件。

- **MHS：预留 adapter 与描述映射位置，不等待它才能动工，也不宣称现在已兼容完整标准。**

- **Kafka、图数据库、Kubernetes、多个消息总线：MVP 默认不装。** 只有当明确的吞吐、部署或查询问题出现时再引入。



这不是为了极简而极简，而是避免多个系统分别维护“设备状态”“物料位置”和“执行成功”，最后谁都不是可信的权威来源。

# 十一、MVP：2–3 个设备 \+ 1 台机器人，怎样走到真正闭环

---

## 11\.1 建议的实验单元



选择一个低风险、可独立验证的任务：**分液设备 \+ 天平 \+ 可选相机 \+ 一台机械臂。**



以水和标准容器进行分配、搬运、称量与参数校准。优先采用固定工装和明确交接点，不要一开始就要求机器人面对任意位置、任意容器和任意抓取。



这个选择的价值在于：物料变化有可测量反馈，运动与仪器操作都有代表性，但科学过程足够简单，便于检验基础设施本身。

## 11\.2 阶段一：只读 Twin，不从精美 3D 开始



建立设备、容器、样品、位置、耗材与能力注册表；接入真实状态、时间戳、校准信息与错误。



空间部分先定义机器人基座、设备交接点、相机坐标和固定工位。界面可以先是二维布局。



这一阶段的验收问题是：

> Agent 能否可靠回答“这份样品在哪里、有哪些操作可用、为什么当前不能执行”？
>
>



失联设备必须显示未知或过期，不能继续显示最后一次的“ready”。

## 11\.3 阶段二：Simulation 与故障注入



为每个真实能力提供相同契约的 fake backend，模拟状态变化、耗时和物料消耗。



重点测试不是动画是否逼真，而是：**目的地占用、耗材不足、单位错误、状态过期、命令执行前失联、命令执行后回执丢失、抓持失败、部分转移完成。**



机器人动作需要时增加运动学和碰撞验证。



验收标准：

> 同一计划可在仿真环境运行；故障不会导致错误的“成功”，也不会触发未经判断的物理重试。
>
>

## 11\.4 阶段三：先跑确定性 Real Workflow



先不让 Agent 自由规划，执行经批准的固定流程：

```Plain Text
确认资源与校准
→ 准备容器
→ 分配水
→ 机器人搬运
→ 称量
→ 验证与记录
→ 返回或进入下一检查点
```



按风险评估完成真实设备调试、互锁检查和监督运行。测试控制进程重启、网络中断与人工接管后的恢复。



此时应能证明：**任务重启不会重做已发生但回执丢失的动作；样品位置无法确认时会停止推进；急停和保护功能不依赖 Agent。**



这比提前展示“自然语言跑实验”更重要。

## 11\.5 阶段四：接入有边界的 Agent Closed Loop



允许 Agent 在批准范围内选择下一次分配参数或实验条件，目标是降低称量偏差或比较参数效果。



闭环成为：

```Plain Text
Agent 提出下一次实验
→ Runtime 检查能力、资源、预算与条件
→ 仿真 / 验证
→ 真实执行
→ 获取称量与过程观测
→ 经审核的分析程序计算质量指标
→ Agent 决定下一步
```



明确限制总实验次数、物料消耗、允许参数空间、可调用能力及失败后的升级路径。Agent 不能修改驱动、标定或安全配置。



验收应关注：**可追溯性、结果质量、故障分流、资源正确性与无人干预成功率**，而不是只看任务是否最终结束。测试数量应根据风险与可靠性目标制定，不能用“连续跑过若干次”代替安全论证。

## 11\.6 阶段五：按瓶颈扩展，而不是按产品清单扩展



增加第三台仪器后，先解决真实的交接与材料语义。



出现多个并行实验，再增加调度与资源竞争管理。出现移动机器人和共享通道，再考虑车队协调。出现视觉泛化问题，再考虑更高保真的感知仿真。出现多场景资产协作，再引入 USD。



同时，把补液、换耗材、清洁、校准、废弃物处理和维护也纳入资源与任务模型。



**实验协议自动执行，不等于整个实验室已经具备持续黑灯运行能力。**

# 十二、最终建议

---

如果今天启动这个项目，我会确立三个不可动摇的架构选择：

- **第一，Agent 面对的是经过授权的能力契约，不是底层协议，也不是任意硬件 Shell。**

- **第二，系统中心是持久化执行与有证据的世界状态，而不是 3D 场景或某个 Twin Platform。**

- **第三，所有物理动作都必须明确回答：执行前需要什么、执行中不能违反什么、执行后凭什么确认、失败时哪些事实仍然未知。**



从 MHS 借鉴自描述、发现和多入口调用；从 WoT/LabThings 借鉴轻量设备描述；从 UniLabOS/MADSci 借鉴资源、位置和执行语义；从 PyLabRobot、Bluesky、ROS 2/MoveIt 复用专业能力。



但最终需要你自己拥有的，不是又一个庞大平台，而是这条最小、完整的责任链：

> **Agent 提出意图 → Runtime 批准并预约 → 本地执行器执行 → 独立观测验证 → 世界状态更新 → Agent 获得可信反馈。**
>
>



**Agent\-native 的本质不是让模型承担更多隐含责任，而是把过去依赖实验员经验、现场协调和口头约定的责任，变成机器可理解、运行时可强制执行的契约。**



MHS 的正式规范、驱动开放情况和关键项目许可仍在变化，值得设为月度跟踪项。需要设置这项更新吗？
